# MCP 2026-07-28 Dual-Era Server, Design Spec
**Date:** 2026-09-09
**Round:** clipmetamcp protocol upgrade (spec risk R3 from the original MCP server spec, now due)
**Author:** Peckworks Lab
**Status:** design, not yet built. Branch-only work; merging to `main` is a separate decision.

---

## Problem Statement

`clipmetamcp` implements the Model Context Protocol (MCP) by hand, with no SDK dependency. It claims revisions `2025-11-25` and `2025-06-18`, both of which open with an `initialize` handshake that negotiates the protocol version once per process.

MCP revision **2026-07-28** (verified current at modelcontextprotocol.io on 2026-09-09, no newer draft) makes the protocol **stateless**: the handshake is gone, every request carries its own protocol version and client capabilities in a `_meta` field, and the server must answer a new `server/discover` request. The revision also removes `ping`, requires a `resultType` on every result, and requires cache hints on list results.

The design problem is not "add a version string." Our negotiation lives inside `HandleInitialize`, and the new revision deletes `initialize`. The question is:

> How does one dispatch loop serve a legacy client that opens with `initialize` AND a modern client that fires `tools/call` cold with `_meta` on it, without either era contaminating the other?

The spec's own answer, in its own words, is a **dual-era server**: "A request carrying modern per-request `_meta` is served statelessly according to this revision. An `initialize` request selects legacy semantics." Era is decided **per request**, never cached on the process. This spec builds exactly that.

**Decision already made (2026-09-09):** keep the hand-rolled protocol layer. The official C# SDK 2.0.0 exists and implements this revision, but adopting it would delete the one part of this repo that is hard to acquire (a from-spec protocol implementation) and break the zero-NuGet rule. The SDK source is a reference to read, not a dependency to take.

---

## Scope

**In scope:**
- Serve revision `2026-07-28` to modern clients: per-request `_meta` parsing, `server/discover`, `resultType`, `serverInfo`, `ttlMs`/`cacheScope`, `UnsupportedProtocolVersionError`.
- Keep the legacy path (`initialize`, `ping`, `notifications/initialized`, revisions `2025-11-25` and `2025-06-18`) working **byte-for-byte**.
- Per-request era classification with no cross-request state.
- Tests for each era alone and both interleaved on one session.
- Extend the built-in `--self-test` with a modern `server/discover` check.
- Update durable docs (CLAUDE.md, PITFALLS if a gotcha surfaces, release notes at the next release).

**Out of scope:**
- Streamable HTTP transport, routing headers, session ids, SSE. We are stdio only.
- Multi Round-Trip Requests (`resultType: "input_required"`). No tool needs mid-call client input today.
- `subscriptions/listen`, `notifications/*/list_changed`. Our tool list never changes at runtime.
- Roots, Sampling, Logging (all deprecated in this revision; we implement none of them).
- Tasks extension, extensions negotiation, icons.
- `MissingRequiredClientCapabilityError` (`-32021`). We require no client capabilities, so it can never fire.
- Adopting the MCP SDK.
- A version bump. That happens at release time via `bump-version.ps1`, not in this branch.

## 1. Era Model

Three named eras, matching the spec's terminology:

| Term | Meaning here |
|---|---|
| **Modern** | A request whose `params._meta` carries `io.modelcontextprotocol/protocolVersion`. Served statelessly per `2026-07-28`. |
| **Legacy** | Any request without that key. Served exactly as today (`2025-11-25` / `2025-06-18` semantics). |
| **Dual-era** | This server: both, on the same stdio process, decided per request. |

**The one rule that everything else protects:** classification reads only the request in hand. `McpSession` gains no field that remembers which era a previous request used. The spec is explicit: "Servers MUST NOT rely on prior requests over the same connection to establish context." A cached "this client is modern" flag would quietly rebuild the session the revision deleted.

Why the legacy path stays gate-free: today the server answers `tools/list` without requiring a prior `initialize`, and that stays. A legacy request is simply "no modern `_meta`," and the existing switch handles it. This is also what makes byte-for-byte legacy preservation cheap: the legacy code path does not change, it just gets a new front door.

Edge case, decided: an `initialize` request that also carries modern `_meta` is classified **modern** (the `_meta` check runs first), and modern has no `initialize`, so it gets Method Not Found. The error message names the modern versions we support, per the spec's advice that legacy clients "have no fall-forward mechanism, and this message may be the only diagnostic they can surface."

## 2. Version Constants

Two lists, because the two eras cannot share one:

```csharp
/// Newest revision this server implements. Verified current at
/// modelcontextprotocol.io on 2026-09-09 (spec risk R3: re-check on upgrade).
public const string LatestProtocolVersion = "2026-07-28";

/// Modern (per-request _meta) revisions. Advertised by server/discover and in
/// UnsupportedProtocolVersionError.data.supported. A legacy client cannot use
/// these, it never sends _meta, so they never appear in the legacy list.
public static readonly IReadOnlyList<string> ModernProtocolVersions = ["2026-07-28"];

/// Newest legacy (initialize-handshake) revision; what initialize answers when
/// the client asks for something we do not serve.
public const string LatestLegacyProtocolVersion = "2025-11-25";

/// Legacy revisions, unchanged. 2025-03-26 stays excluded (JSON-RPC batching).
public static readonly IReadOnlyList<string> SupportedProtocolVersions =
    ["2025-11-25", "2025-06-18"];
```

`HandleInitialize`'s fallback changes from `LatestProtocolVersion` to `LatestLegacyProtocolVersion`. That is the only edit inside the legacy path, and it preserves today's wire output exactly (`2025-11-25`).

The `2025-03-26` exclusion note is precedent: we only claim revisions our surface honestly serves. Adding `"2026-07-28"` to `ModernProtocolVersions` is the **last** implementation step, after every modern behaviour is in place and tested.

## 3. Request Metadata (`RequestMeta`)

New file `clipmetamcp/Protocol/RequestMeta.cs`. A small immutable record parsed from `params._meta`, pure and unit-testable without a session:

```csharp
public sealed record RequestMeta(string ProtocolVersion, bool HasClientCapabilities)
{
    public const string ProtocolVersionKey    = "io.modelcontextprotocol/protocolVersion";
    public const string ClientCapabilitiesKey = "io.modelcontextprotocol/clientCapabilities";
    public const string ClientInfoKey         = "io.modelcontextprotocol/clientInfo";
    public const string ServerInfoKey         = "io.modelcontextprotocol/serverInfo";

    /// Returns null when params carry no modern protocolVersion (a legacy request).
    public static RequestMeta? TryParse(JsonNode? requestParams);
}
```

The detail most implementations get wrong: these are **flat string keys containing a slash**, not nested objects. `_meta["io.modelcontextprotocol/protocolVersion"]`, never `_meta.io.modelcontextprotocol.protocolVersion`. `TryParse` reads the literal key.

Validation order on a modern request, each step short-circuiting:

1. `protocolVersion` present but not in `ModernProtocolVersions` (a legacy version string like `2025-11-25` sent in `_meta` lands here too): **`UnsupportedProtocolVersionError`**, code `-32022`, `data: { supported: [...ModernProtocolVersions], requested: "<what they sent>" }`.
2. `clientCapabilities` absent or not an object: **Invalid Params** `-32602`, message names the missing key. The spec: "A request missing any required field is malformed; the server MUST reject it with `-32602`."
3. Otherwise dispatch.

`clientInfo` and `logLevel` are optional and read for logging only. We never emit `notifications/message`, so the `logLevel` rule ("servers MUST NOT emit `notifications/message` for requests that did not include this field") is satisfied by construction.

## 4. Dispatch

`Dispatch` today: reject null id, drop notifications, switch on method. It becomes: reject null id, drop notifications, **classify**, then one of two switches.

```
Dispatch(message)
  ├─ null id            -> Invalid Request (unchanged)
  ├─ notification       -> ignore (unchanged; notifications/initialized is legacy-only, still a no-op)
  ├─ RequestMeta.TryParse(params) is null
  │     -> DispatchLegacy(id, method, params)     today's switch, verbatim
  └─ else
        -> DispatchModern(id, method, params, meta)
```

`DispatchModern`:

| Method | Handling |
|---|---|
| `server/discover` | `HandleDiscover` (new, section 5) |
| `tools/list` | shared list builder + modern envelope (section 6) |
| `tools/call` | shared call executor + modern envelope |
| `initialize`, `ping`, anything else | Method Not Found `-32601`; for `initialize` the message adds "this server speaks 2026-07-28 statelessly; supported modern versions: ..." |

`DispatchLegacy` is today's `switch` moved into its own method, untouched.

The tool handlers are shared. `HandleToolsList` and `HandleToolsCall` split into a **builder** (returns the result `JsonObject`, era-agnostic, contains all the existing logic and comments) and a **writer** per era. Legacy writes the builder's object as-is. Modern passes it through `ModernEnvelope` first.

---

## 5. `server/discover`

Servers MUST implement it. It is the modern client's way of asking before committing, and on stdio it is the recommended backward-compatibility probe. Response, built from the same constants the rest of the server uses:

```json
{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": { "tools": {} },
    "_meta": { "io.modelcontextprotocol/serverInfo": { "name": "clipmeta", "version": "1.1.0" } },
    "ttlMs": 3600000,
    "cacheScope": "public"
  }
}
```

`supportedVersions` is `ModernProtocolVersions`, not the legacy list. A client that reads this list will send `_meta` on its next request, so only versions that work with `_meta` may appear. `instructions` is omitted; tool descriptions already carry the guidance.

`server/discover` itself goes through the same `_meta` validation as every other modern request. A discover carrying an unsupported version gets `UnsupportedProtocolVersionError` with the supported list in `data`, which is exactly what the spec's probe sequence expects.

## 6. Modern Result Envelope

Every modern result gets, via one helper `ModernEnvelope(JsonObject result, bool cacheable)`:

- `resultType: "complete"` (REQUIRED on every result in this revision).
- `_meta["io.modelcontextprotocol/serverInfo"] = { name, version }` (SHOULD, on every result).
- When `cacheable`: `ttlMs` and `cacheScope` (REQUIRED on `server/discover` and `tools/list`; `tools/call` is not cacheable and gets neither).

Constants, named, with the reasoning next to them in code:

```csharp
/// The tool list is fixed for the life of the executable; a new exe is a new
/// process, which invalidates any client cache anyway. One hour matches the
/// spec's own example and keeps a stale cache bounded if a client ever shares
/// one across restarts.
private const int ToolListTtlMs = 3_600_000;

/// The list is identical for every caller and carries no user data, so any
/// shared cache may serve it. (The LIBRARY contents are user data; the tool
/// DEFINITIONS are not.)
private const string ToolListCacheScope = "public";
```

`tools/call` results are unchanged in shape (`content`, `structuredContent`, `isError`) plus the two universal fields. Tool handlers do not know which era called them.

---

## 7. JSON-RPC Layer Changes

`JsonRpc.cs`:

- `JsonRpcErrorCodes.UnsupportedProtocolVersion = -32022` with a doc comment citing the revision's error-code policy (`-32020` to `-32099` reserved for the spec; we emit only defined codes with their defined meanings).
- `JsonRpcWriter.WriteError` gains an optional trailing `JsonNode? data = null` parameter, serialized as `error.data` when non-null. Existing callers are untouched.

Nothing else in the JSON-RPC layer changes. Framing, parse-error handling, null-id rejection, and notification classification are all era-independent and already correct for this revision (the stdio page's message rules are unchanged).

---

## 8. Self-Test

`clipmetamcp/SelfTest.cs` drives the real binary through a scripted stdio conversation (`initialize`, `notifications/initialized`, `ping`, ...). It gains one modern check after the legacy ones: a cold `server/discover` with `_meta`, asserting `resultType == "complete"` and that `supportedVersions` contains `LatestProtocolVersion`. This is the only in-repo check that exercises the era split through the actual process boundary rather than the in-memory harness.

## 10. Test Strategy

Existing tests must pass unchanged except the one-line harness pin. That is the byte-for-byte legacy guarantee, enforced by the suite that already exists.

New tests, all through `McpHarness` unless noted:

**RequestMeta (pure):**
- no params, params without `_meta`, `_meta` without the version key: all return null (legacy).
- version key present: parsed; `HasClientCapabilities` true only when the key is a JSON object.
- the nested-object trap: `_meta: { io: { modelcontextprotocol: { protocolVersion: ... } } }` returns null (we read the flat key only).

**Modern alone:**
- `server/discover` cold, no prior traffic: `resultType`, `supportedVersions == ModernProtocolVersions`, `capabilities.tools`, `serverInfo` name + version, `ttlMs >= 0`, `cacheScope == "public"`.
- `tools/list` cold: full tool set, plus the four envelope fields.
- `tools/call` cold (an unconfigured-sandbox refusal is enough): `resultType`, `serverInfo`, `isError`, and **no** `ttlMs`/`cacheScope`.
- unsupported version in `_meta`: `-32022`, `data.supported`, `data.requested` echoed.
- a legacy version string (`2025-11-25`) inside `_meta`: `-32022` (modern-era request, not a modern version).
- missing `clientCapabilities`: `-32602`.
- `ping` with modern `_meta`: `-32601`.
- `initialize` with modern `_meta`: `-32601`, message contains `2026-07-28`.

**Legacy alone:**
- `initialize` requesting `2026-07-28` (no `_meta`) answers `LatestLegacyProtocolVersion`. This pins the fallback change from section 2.
- legacy `tools/list` result carries **no** `resultType`/`ttlMs`/`cacheScope` (byte-for-byte guard).

**Interleaved on one session (the test that proves the design):**
- modern `tools/list`, then legacy `initialize`, then modern `server/discover`, then legacy `ping`, then modern `tools/call`. Each response is checked for its own era's shape. This fails the moment anyone adds a "current era" field to the session.

**External check (manual, owner's machine, recorded in the PR):**
- MCP Inspector against the built exe: confirm it discovers `2026-07-28`.
- Reinstall the `.mcpb` in Claude Desktop and run one read tool. Claude Desktop's client era is unknown at time of writing; dual-era means it works either way, but that claim needs one real observation, not an assumption.

## 11. Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | Claude Desktop is still a legacy client and something in the legacy path regressed. | Legacy path is moved, not rewritten; existing suite unchanged; manual reinstall check before merge. |
| R2 | Session state creeps in ("remember the client is modern"). | The interleaved test; code review rule: `McpSession` gains no era field. |
| R3 | Spec drift. `2026-07-28` is "current," so it may receive backward-compatible additions. | Verification date in the constant's doc comment (this is the R3 pattern from the original spec, kept). Re-check on the next upgrade. |
| R4 | A modern client reads `supportedVersions` and expects legacy versions there. | Spec says the list is for subsequent modern requests; legacy versions cannot be used with `_meta`. Documented at the constant. |
| R5 | Surface-wide test assertions outside the diff. | Run the full `clipmetamcp.Tests` project, never a `--filter`. |
| R6 | Half-migrated `main` during an interview about MCP servers. | Branch-only until the owner says merge. |
| R7 | Legacy `initialize` output silently changes when `LatestProtocolVersion` is bumped. | `HandleInitialize` falls back to `LatestLegacyProtocolVersion`, and a test pins that `initialize` requesting `2026-07-28` still answers `2025-11-25`. |

## 12. Implementation Order

Each step leaves `dotnet build` at 0/0 and `dotnet test` green, and is independently committable.

1. Constants only: add `LatestLegacyProtocolVersion` and `ModernProtocolVersions` (containing `"2026-07-28"`, nothing reads it yet), point `HandleInitialize` at the legacy constant, pin the harness. Add the R7 test. No behaviour change on the wire.
2. `JsonRpc.cs`: error code and `data` overload. No caller yet.
3. `RequestMeta` + its pure tests.
4. Dispatch split: `DispatchLegacy` (moved switch) and `DispatchModern` with the `_meta` validation from section 3 and Method Not Found for every method. Classification wired in. The version-error, missing-capabilities, `ping`, and `initialize` modern tests land here, and the interleave test can be written against error shapes.
5. Builder/writer split of the tool handlers + `ModernEnvelope`. Modern `tools/list` and `tools/call` go live; their tests and the full interleave test land here.
6. `HandleDiscover` and its tests.
7. Make `"2026-07-28"` the `LatestProtocolVersion`. This is the step that changes what the server *says* it is, and it comes after every modern behaviour exists and is tested. (Nothing on a branch is released, so the "claim last" discipline is about this constant and the eventual merge, not about the internal list that the tests need from step 4 onward.)
8. Self-test check. Docs. Full test run.
9. Manual: Inspector + Desktop reinstall. Record results in the PR.
