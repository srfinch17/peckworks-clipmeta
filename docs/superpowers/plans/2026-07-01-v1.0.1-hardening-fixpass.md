## PART B, Code fixes (TDD each; MAJORs first)

### Task B1 (MAJOR): Strict reads in BigEndianReader, one truncated clip must not brick the library

**The demonstrated failure:** `BinaryReader.ReadBytes` returns a *short array* at
EOF instead of throwing; `BitConverter.ToUInt64` then throws `ArgumentException`
("The array starting from the specified index is not long enough…"), outside the
parser's documented `InvalidDataException` contract and outside every directory
scanner's catch list. A 15-byte file (`size=1` extended-size header truncated at
EOF) makes `clipmetascribe <dir> --find/--index` die with a raw stack trace that
never names the offending file, and bricks all four MCP library tools
(`library_find/index/vocab/export`).

- [ ] **Failing tests first:** (a) a 15-byte truncated file through the single-file
      read path → expect a clean `InvalidDataException`-derived error, correct
      exit code per `Program.cs:644`'s contract; (b) a directory scan containing
      one truncated file + good files → scan completes, good files indexed,
      error output **names the bad file's path**.
- [ ] Fix `clipmeta.core/Mp4/BigEndianReader.cs`: add a private
      `ReadExactly(BinaryReader reader, int count)` helper that checks the
      returned length and throws `EndOfStreamException` on short read. Route
      `ReadUInt32` (line ~20), `ReadUInt64` (line ~28), `ReadFourCC` (line ~40),
      and any other `ReadBytes` call sites in the file through it. (The parser's
      existing handlers already convert `EndOfStreamException` →
      `InvalidDataException`, verify this holds for every entry point.)
- [ ] Harden the scanner error paths so a per-file parse failure is caught,
      reported **with the file path**, and skipped: `ClipMetaFinder.cs:12/25-28`,
      `ClipMetaIndex.cs:87-90`, and the MCP library tools' per-file loops.
- [ ] Commit: `fix: strict EOF handling in BigEndianReader; scanners skip and name bad files`

### Task B2 (MAJOR): Refuse files with editable metadata outside the canonical location

**The demonstrated failure:** ISO 14496-12 permits `meta` directly under `moov`
(and `udta` under `trak`). The reader (`ClipMetaReader.cs:38-57`) walks every
`ilst` anywhere; the writer (`Mp4Writer.cs:1150-1156` `FindIlst`) only knows
`moov→udta→meta→ilst`. On a spec-legal file with `moov.meta.ilst` containing
`game=old`: `--set game new` exits 0 and produces **both** values (duplicate-key
JSON on export, both match on find); `--clear game` reports success but the value
survives; `--clear-all` is permanently impossible (exit 3).

- [ ] **Failing tests first:** craft a file with metadata at `moov.meta.ilst`
      (parser already reads this shape). Assert `--set`, `--clear`, `--clear-all`
      each **refuse** with a clear message and the original stays byte-identical;
      read paths (`--list`) still work.
- [ ] Fix: in the pre-write gate (alongside `DetectFragmented` /
      `VerifyParseAccountsForWholeFile`), search the whole tree for any `ilst`
      or node with a set `EditableKey` that is **not** under the canonical
      `moov.udta.meta.ilst` path; if found, throw the same refusal-style
      exception the fragmented-MP4 path uses, with a message like:
      *"metadata found at a non-canonical location (moov.meta); clipmeta only
      edits moov.udta.meta.ilst and will not risk a divergent write, file
      refused."* This matches the writer's refuse-don't-guess philosophy
      (~20 lines).
- [ ] Commit: `fix: refuse writes to files with editable atoms outside moov.udta.meta.ilst`

### Task B3 (MAJOR): Post-write verification must compare values, not just existence

**The confirmed gap:** `Mp4Writer.cs:1124-1131`, the comment says "Every field
this mutation stored must read back," but the loop only checks
`FindEditableNode(root, key) != null`, searching the **whole tree**. A
value-corrupting bug in `FreeformAtomWriter` or normalization would verify clean;
finding B2 proves a stale atom elsewhere already satisfies it today.

- [ ] **Failing test first:** a write verified against a tree where the only
      matching atom holds the *wrong value* (or sits outside the canonical path)
      must throw.
- [ ] Fix `VerifyWrite`: for each `(key, value)` in `mutation.SetFields`, locate
      the node **under the canonical `moov.udta.meta.ilst`** (via `FindIlst`,
      not the whole-tree `FindEditableNode`), and compare its parsed read-back
      value against the normalized written value; throw with expected-vs-actual
      on mismatch. Keep the existing missing-atom throw. Apply the same
      canonical-path constraint to the `ClearAll` leftover check and deleted
      fields.
- [ ] Commit: `fix: post-write verification compares read-back values at the canonical path`

### Task B4 (MAJOR): Cross-process serialization for writes and the tag queue

**The gap:** all concurrency control is per-process (`WriteGate.cs:14` is an
in-process `SemaphoreSlim`; its lines 8-10 overclaim that the File.Replace race
is "retired permanently"), but deployment is explicitly multi-process: an MCP
server per host app (Claude Desktop AND Claude Code) plus `clipmetascribe`
batch/`--flush-queue`. Failure modes: (1) `TagQueue.Drain`
(`TagQueue.cs:59-75, 155-199`) holds queue state in memory across multi-second
MP4 writes then saves survivors, a concurrent `Enqueue` from another process is
silently overwritten (a spoken tag vanishes); (2) two processes both snapshot the
same clip, both `File.Replace`, the loser's committed fields are silently
discarded (never torn, but stale-based).

- [ ] Add a small cross-process lock utility in `clipmeta.core` (e.g.
      `CrossProcessLock`): a named `Mutex` whose name is derived from the
      canonicalized (full, case-normalized) path of the resource, the queue
      file for queue operations, the target MP4 for writes. Acquire with a
      bounded timeout (~30 s) and a clear timeout error; handle
      `AbandonedMutexException` (treat as acquired, previous holder died).
- [ ] Wrap: `TagQueue` load→mutate→save spans (`Enqueue`, `Drain`, any other
      read-modify-write), the `Mp4Writer.WriteMetadata` pipeline (parse→temp→
      verify→Replace), and make `WriteGate` delegate to it so MCP and CLI share
      the same lock. CLI write/flush paths must go through it too.
- [ ] Correct the overclaiming comments: `WriteGate.cs:8-10` and
      `Mp4Writer.cs:255-269` (the worst case of the swap window is a
      stale-based write discarding a concurrent writer's fields, say so).
- [ ] **Tests:** two concurrent in-process drains/writes serialize correctly
      (named mutexes work in-process too); if a spawned-child-process test is
      feasible without flakiness, add one; otherwise document the manual
      verification performed. Do not rabbit-hole on process-spawning test infra.
- [ ] Commit: `fix: cross-process named-mutex locking for MP4 writes and the tag queue`

### Task B5: Clear refusal for moov-less (and swallowed-moov) files

**Two convergent findings.** (a) Correctness reviewer: a well-formed `ftyp`+`mdat`
file (no `moov`, not fragmented) falls through `DetermineScenario` as `Create`,
never emits a moov, and dies at the temp-length check with the baffling internal
message "temp file is X bytes but Y were expected". (b) Nemesis: a to-EOF
(`size=0`) box that is **not last** (`BigEndianReader.cs:70-74` resolves size-0
unconditionally to EOF) silently swallows everything after it including `moov` , 
reads report "(no clipmeta metadata)" with false confidence, writes die with the
same internal message.

- [ ] **Failing tests first:** (a) `ftyp`+`mdat` file → write refused with a
      first-class "no moov box found, not a complete/finalized MP4" error;
      (b) a file with `mdat(size=0)` followed by `moov` → same clean refusal on
      write (and, if cheap, a parse-level warning flag when a size-0 box is not
      last).
- [ ] Fix: explicit guard next to `DetectFragmented` in the write path:
      `if (!root.Children.Any(c => c.Type == "moov")) throw ...` with a message
      that mentions the size-0/truncated-recording possibility.
- [ ] If low-effort: record a parser-level note when a size-0 box is followed by
      no siblings but started before other data was expected (nice-to-have; skip
      if it turns into surgery, the write-path guard is the required part).
- [ ] Commit: `fix: first-class refusal for MP4s with no moov box`

### Task B6: CLI `--backup` must use the ClipBackup naming convention

**The confirmed drift:** `clipmetascribe/Program.cs:307, 429, 504` build
`filePath + ".bak"` while `clipmeta.core/Write/ClipBackup.cs:22-27` centralizes
timestamped `.bak-yyyyMMdd-HHmmss` naming precisely "so the writer … and the
management tools … can never drift apart." Consequences: the second CLI backup
silently destroys the first via `File.Replace`, and CLI backups are invisible to
`library_list_backups` / `clip_restore_backup` / `clip_prune_backups`.

- [ ] **Failing test first:** two consecutive CLI `--backup` writes must yield
      two distinct backup files matching the timestamped pattern.
- [ ] Fix: all three `Program.cs` sites call `ClipBackup`'s path factory
      (mirror `WriteTools.cs:599`).
- [ ] Commit: `fix: CLI --backup uses the centralized timestamped backup naming`

### Task B7: Index format must round-trip field names containing spaces

**The demonstrated failure:** `ClipMetaIndex.cs:124` writes
`field {Escape(field)} {Escape(value)}` space-delimited, and `Escape` does not
escape spaces; the reader (~line 175) splits at the first space. `--set
"kill count" 5` stores fine in the MP4 but `--index-search "kill count" 5` finds
nothing while `--index-search kill "count 5"` finds it, the cached index and
live `--find` silently answer the same question differently.

- [ ] **Failing test first:** round-trip an index entry with field `kill count`;
      `--index-search "kill count" 5` must find the clip and agree with `--find`.
- [ ] Fix: extend the existing `Escape`/`Unescape` machinery to escape spaces
      (existing index files without spaces must parse identically, verify with
      a test against the current format). Rejecting whitespace field names at
      the mutation boundary is the fallback if escaping gets hairy, but escaping
      is preferred (files tagged by other tools may already carry such names).
- [ ] Commit: `fix: index format round-trips field names containing spaces`

- [ ] `clipmetamcp/Protocol/McpSession.cs:44-56` `ReadAssemblyVersion()` is a
